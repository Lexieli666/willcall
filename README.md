# Willcall

Willcall sells a fixed inventory of seats to a crowd that arrives all at once.

Ten thousand people press the button at 10:00:00 for five thousand seats. Most of them will not get
one. The ones who do must actually get it — not a confirmation that is later revoked — and the ones
who do not must find out quickly and fairly. The seat map works with a keyboard alone or a screen
reader alone, and CI blocks any merge that breaks that.

Java 21 · Spring Boot 3 · PostgreSQL 16 · Redis 7 · Server-Sent Events · React 19 · TypeScript 5 ·
k6 · Terraform

---

## The invariant

**For every event: `confirmed + unexpired holds <= capacity`, and no seat has more than one active
allocation.**

It is defended at four independent levels, so a bug has to defeat all four to sell a seat twice:

1. **The schema.** A partial unique index permits at most one `ACTIVE` hold per seat. Order lines
   are written only on confirmation, so a plain unique index means "sold at most once".
2. **The transaction.** Every acquisition locks its seat rows before writing, in one order
   everywhere — [ADR 0005](docs/adr/0005-one-lock-order-holds-then-seats.md). There is no
   unprotected read-then-write in the reservation core.
3. **The tests.** Ten thousand simultaneous attempts at five hundred seats, fifty times, asserting
   exactly five hundred successes and zero oversells; plus a model-based property test comparing
   random command sequences against an independently written reference machine.
4. **An external check.** [`scripts/verify-invariants.sh`](scripts/verify-invariants.sh) queries the
   database directly, so it catches violations the application cannot see. It runs in CI, after
   every load test, and at the end of every game day.

PostgreSQL owns correctness; Redis only accelerates. Losing Redis degrades the queue and leaves
reservations correct — proved by a test that stops Redis mid-run and then checks the invariant.
[ADR 0001](docs/adr/0001-postgresql-owns-correctness-redis-only-accelerates.md)

### Where the numbers came from being wrong

Three of the measurements above changed materially during the build, and in each case the
measurement was wrong before the software was:

- **Memory per connection** was first reported as 212 KiB by sampling resident set before and
  during a run — which attributed the garbage from delivering fifteen million messages to the
  connections. Forcing a collection and comparing the heap with connections open against the heap
  after closing them gave 90.5 KiB for identical code.
- **The seat map's render time** was 126 ms against a 120 ms budget, and nothing in the code looked
  expensive. `formatMoney` was constructing an `Intl.NumberFormat` per seat while composing
  accessible names — five thousand of them per render. Caching took it to 42 ms.
- **The segment tree's crossover** was predicted to be a row size. It is an occupancy level: at 10%
  occupancy a linear scan wins at every size including 20,000 seats per row, and at 90% the tree
  wins everywhere. The prediction is published alongside the measurement that contradicted it.

## Architecture

```
  browser (React 19 + TypeScript)                k6 · Node SSE generator
    REST/JSON  +  SSE (snapshot + deltas)        (fd limits, ephemeral ports tuned)
             |
   Java 21 / Spring Boot 3 modular monolith (3 replicas behind a load balancer)
     catalog | reservation | waiting room | realtime | allocation | payment
             |                 |                   |
        PostgreSQL 16       Redis 7           Redis pub/sub
   source of truth:      waiting-room ZSET,   cross-replica seat-delta bus
   seats with version,   admission tokens,
   SELECT ... FOR UPDATE rate limits
   SKIP LOCKED, outbox
```

A modular monolith, not microservices — the reservation core's correctness rests on a single
transaction, and splitting it would put that transaction across a network boundary.
[ADR 0003](docs/adr/0003-modular-monolith-not-microservices.md). Module boundaries are enforced by
a test that reads the source and fails the build when one erodes.

### The parts worth reading

| Area | What is interesting about it |
|---|---|
| [Reservation core](server/src/main/java/dev/willcall/reservation/service/ReservationService.java) | One lock order everywhere; checkout split into three steps so the payment gateway is never called while holding row locks |
| [Idempotency](server/src/main/java/dev/willcall/reservation/service/IdempotencyService.java) | Releases its key on failure, because a charge that succeeded behind a timeout must be completable by the retry — [ADR 0006](docs/adr/0006-idempotency-releases-its-key-on-failure.md) |
| [Segment tree](server/src/main/java/dev/willcall/allocation/RowAvailabilityTree.java) | Prefix and suffix runs per node, so a run straddling two children is found; benchmarked against a linear scan |
| [SSE hub](server/src/main/java/dev/willcall/realtime/EventStreamHub.java) | Coalescing and gap detection interact badly; frames carry a sequence *range* — [the protocol](docs/realtime-protocol.md) |
| [Waiting room](server/src/main/java/dev/willcall/waitingroom/WaitingRoomService.java) | Token-bucket admission in one Lua script, so every replica admits without a leader election |
| [Seat map](web/src/components/SeatMap.tsx) | Real DOM, ARIA grid, roving tabindex, 5,000 seats inside a render budget — [ADR 0009](docs/adr/0009-seat-map-as-real-dom.md) |

## Scope

Read [docs/product-scope.md](docs/product-scope.md) for the product argument.

**In scope** — venues, events, sections, rows, seats, price tiers; the seat lifecycle
`available → held(expiry) → sold` plus blocked; exact-seat and best-available-*N*-together
acquisition; holds with a TTL and a sweeper; idempotent checkout; a fake payment gateway that can
fail, time out, or succeed *after* timing out; a fair waiting room; live seat state over
Server-Sent Events; a React front end with an organizer dashboard; Prometheus metrics,
OpenTelemetry traces, Grafana dashboards and SLOs; k6 load scripts; a one-million-row seeded
dataset; Docker; Terraform; deploy on merge.

**Not in scope** — real payments; seller onboarding; search and recommendations; email and SMS;
fraud detection beyond rate limits; native mobile; Kafka; Kubernetes; microservice decomposition.

## Running it

Requirements: Docker with Compose v2, JDK 21, Node 20.

```bash
make up                       # three replicas behind the local edge proxy
open http://127.0.0.1:8080
```

| Command | What it does |
|---|---|
| `make up` / `make down` / `make clean` | The three-replica stack that every load test targets |
| `make dev` | One replica plus the Vite dev server |
| `make test` | Backend unit and property tests, frontend unit tests |
| `make integration` | Testcontainers: real PostgreSQL and Redis |
| `make test-long` | The same suites at long-mode repetition counts |
| `make e2e` | Playwright, including the axe and keyboard-only passes |
| `make lighthouse` | Lighthouse budgets |
| `make lint` | Spotless, Error Prone, ESLint, `tsc` |
| `make verify-invariants` | Assert the invariant directly against the database |
| `make bench` | JMH: segment tree against linear scan |
| `make load-smoke` / `make load-flash` / `make load-sse` | k6 and the SSE generator |
| `make seed` | The million-row dataset and its query plans |

`make help` lists everything. Observability is a separate profile so it does not compete with a
load run for CPU:

```bash
docker compose --profile observability up -d
open http://127.0.0.1:3000     # Grafana, dashboards provisioned
```

## Limitations

Stated here rather than left for a reader to discover.

- **Nothing has been deployed to AWS.** No credentials on the build host. Every measurement is
  local, every result file says so, and the deploy workflow skips rather than fails when no cloud
  role is configured — a red X on main should mean the code is broken, not that there is no
  account.
- **The manual screen-reader passes have not been done.** Ten checks are listed as outstanding in
  [docs/accessibility.md](docs/accessibility.md). axe and Lighthouse cover what a machine can
  decide; whether an announcement is *useful* needs a person.
- **No public demo with real users**, so [ADR 0012](docs/adr/0012-hold-ttl.md) stays `proposed` and
  the 120-second hold TTL remains an unvalidated default. Synthetic load cannot settle it: a load
  script checks out in whatever time it is told to, and does not hesitate or go and find a wallet.
- **Memory per SSE connection misses its target.** 75.7 KiB against 10–60 KB. Closing the gap needs
  a non-blocking writer pool instead of a thread per connection, which is a redesign.
- **Propagation is not measured in production**, only under load. The server publishes its own
  flush duration; the client half is not instrumented.
- **The load generators share a host with the service.** Percentiles include no network latency and
  do include CPU contention. Every results file repeats this.
